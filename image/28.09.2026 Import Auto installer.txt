ABLAUF-LOGIK: AUTO-IMPORT & KOMPATIBILITAETS-AGENT
====================================================
Reine Planungsskizze (kein Code). Ziel: exakte Begriffe, Datenfelder und
Log-Zeilenformat festlegen, bevor irgendetwas implementiert wird.
 
 
1. DATENFELDER PRO HARDWARE-PROFIL (HARDWARE_INFORMATION)
------------------------------------------------------------
Erfasst einmal pro Programmstart, bevor irgendein fremdes Paket importiert wird.
Feldnamen wie vorgegeben (Grundgeruest):
 
  Feldname        Typ     Quelle                            Zweck
  --------------  ------  --------------------------------  -------------------------------
  CORE            int     os.cpu_count() / psutil            Kern-/Thread-Anzahl (informativ)
  RAM             float   psutil.virtual_memory().total      informativ, evtl. Grenzwert-Filter
  GPU_RAM         float   optional, falls GPU erkennbar       informativ (CUDA-Pakete)
  PLATFORM        str     platform.system()                  Windows / Linux / Darwin
  OS_BITNESS      str     platform.architecture()            32bit / 64bit
  CPU_ARCH        str     platform.machine()                 z.B. AMD64, x86_64, ARM64
 
Zusaetzlich, NICHT Teil der sechs Grundfelder, aber fuer den proaktiven
Vorfilter zwingend noetig:
 
  Feldname        Typ           Quelle                       Zweck
  --------------  ------------  ---------------------------  -------------------------------
  CPU_FLAGS       set[str]      CPUID via ctypes             Menge unterstuetzter Instruction-
                                                               Sets, z.B. {"AVX","AVX2","SSE4"}
  pc_id           str           Vergabe durch Log (PC1,PC2..) kompakter Schluessel im Log
  hw_hash         str           Hash ueber Felder oben        Wiedererkennung derselben Maschine
 
  hw_hash = Hash ueber (CPU_ARCH, PLATFORM, OS_BITNESS, CORE) -- OHNE RAM/GPU_RAM,
  da diese sich z.B. durch RAM-Nachruesten aendern koennen, ohne dass es eine
  "neue" Maschine ist.
  CPU_FLAGS ist eine Eigenschaft, kein Identitaetsmerkmal -> fliesst NICHT in den Hash ein.
 
 
1b. PROAKTIVE AVX/AVX2-ERKENNUNG UEBER patterns_filterung
--------------------------------------------------------------
Das Feld "patterns_filterung" (5. Tupel-Element in LIBRARY_IMPORT/LIBRARY_FROM)
hat zwei verschiedene Inhaltsarten, die getrennt behandelt werden:
 
  a) FAEHIGKEITS-TAGS  (feste Whitelist, siehe unten)
     Beispiel: ["AVX2"], ["AVX", "AVX2", "AVX512"]
     -> werden VOR jedem Importversuch gegen CPU_FLAGS geprueft.
     -> Tag nicht in CPU_FLAGS enthalten => PHASE=FILTER EVENT=SKIP_HW,
        Status=HW_INCOMPATIBLE, kein Import-/Install-Versuch.
 
  b) FEHLERTEXT-MUSTER  (alles, was NICHT auf der Whitelist steht)
     Beispiel: ["0x45a", "WinError 1114"]
     -> werden NUR verwendet, falls trotzdem ein Fehler auftritt
        (zusammen mit der globalen patterns[]-Liste), also reaktiv,
        PHASE=INSTALL EVENT=BANNED.
 
  CPU_CAPABILITY_TAGS (feste Whitelist, bestimmt a) vs. b)):
    { "AVX", "AVX2", "AVX512", "FMA", "BMI2", "SSE4" }
 
  Damit ist z.B. bei torch (["AVX2"]) der komplette Inhalt ein Faehigkeits-Tag
  -> rein proaktiver Check. Bei tensorflow (["AVX","AVX2","0x45a","WinError 1114"])
  sind "AVX"/"AVX2" proaktiv, "0x45a"/"WinError 1114" bleiben reaktiv.
 
 
2. PC-ID VERGABE
------------------
  Format:   PC<N>          Beispiele: PC1, PC2, PC3 ...
  Regeln:
    - kein Unterstrich, kein fuehrendes Nullpadding
    - N steigt rein zaehlend mit jedem neuen hw_hash (kein Wiederverwenden
      von Luecken, falls ein Eintrag jemals entfernt wuerde)
    - naechste freie Nummer = Anzahl bisheriger HW_NEW-Eintraege + 1
 
 
3. BEGRIFFE FUER DEN MODUL-STATUS (pro PC_ID + Modulname)
-----------------------------------------------------------
  Status-Begriff       Bedeutung
  --------------------  --------------------------------------------------------
  UNKNOWN               noch nie versucht auf dieser PC_ID
  HW_INCOMPATIBLE        Vorfilter: Hardware kann es nicht (kein Versuch)
  OK                     Import erfolgreich, Modul im globalen Scope
  RETRYING               Fehler war "harmlos", RETRY_COUNT < MAX_RETRIES
  BANNED                 Fehler passte auf ein patterns_filterung-Muster -> aus
  RETRY_EXHAUSTED        RETRY_COUNT erreicht MAX_RETRIES, kein Hardwarefehler
 
 
4. LOG-ZEILENFORMAT (einzige Datenquelle, keine Zweitdatei)
---------------------------------------------------------------
Ein Eintrag pro Zeile, mit Pipe getrennt, Reihenfolge fix:
 
  [PC_ID] | [JJJJ,MM,TT,hh,mm,ss] | [PHASE] | EVENT=<event> | MODULE=<name|-> | DETAIL=<k:v,k:v,...> | VERSUCH=<n|->
 
  PHASE  = grobe Kategorie, in der der Ablauf gerade steckt
  EVENT  = genauer Ausgang innerhalb dieser Phase
  VERSUCH = Versuchszaehler fuer dieses Modul auf dieser PC_ID ("-" wenn
            der Eintrag keinen Versuchsbezug hat, z.B. HW_NEW, SESSION_START)
 
  DETAIL-Escaping (Entscheidung: JA):
    Vor dem Schreiben werden in jedem Wert innerhalb von DETAIL folgende
    Zeichen ersetzt, damit das Pipe/Komma-Format beim Parsen nicht bricht:
      "|"  -> "\|"
      ","  -> "\,"
      Zeilenumbruch -> " "  (Fehlertexte werden auf eine Zeile reduziert)
    Beim Einlesen wird in umgekehrter Reihenfolge entschaert.
 
  PHASE -> moegliche EVENTs:
 
  PHASE       EVENTs
  ----------  ------------------------------------------------------------------
  HARDWARE    HW_NEW, HW_KNOWN
  SESSION     SESSION_START
  FILTER      SKIP_HW
  IMPORT      IMPORT_OK, IMPORT_FAIL
  INSTALL     INSTALL_TRY, INSTALL_OK, INSTALL_FAIL, RETRY, RETRY_EXHAUSTED, BANNED
  REPAIR      INLINE_REPAIR_TRY, INLINE_REPAIR_OK, INLINE_REPAIR_FAIL
 
  Beispielzeilen:
 
  [PC1]|[2026,09,27,10,15,03]|[HARDWARE]|EVENT=HW_NEW|MODULE=-|DETAIL=hash:8f3a1c,arch:AMD64,os:Windows,flags:SSE4;AVX|VERSUCH=-
  [PC1]|[2026,09,27,10,15,04]|[SESSION]|EVENT=SESSION_START|MODULE=-|DETAIL=-|VERSUCH=-
  [PC1]|[2026,09,27,10,15,05]|[FILTER]|EVENT=SKIP_HW|MODULE=torch|DETAIL=pattern:AVX2,benoetigt:AVX2|VERSUCH=-
  [PC1]|[2026,09,27,10,15,07]|[INSTALL]|EVENT=INSTALL_TRY|MODULE=faiss|DETAIL=pip_name:faiss-cpu|VERSUCH=1
  [PC1]|[2026,09,27,10,15,09]|[INSTALL]|EVENT=BANNED|MODULE=tensorflow|DETAIL=matched_pattern:WinError 1114,fehler_kurz:DLL init failed|VERSUCH=2
  [PC2]|[2026,09,27,11,02,00]|[HARDWARE]|EVENT=HW_NEW|MODULE=-|DETAIL=hash:2b91f0,arch:ARM64,os:Linux,flags:SSE4;AVX;AVX2|VERSUCH=-
 
  Hinweis: mehrere CPU_FLAGS-Werte innerhalb EINES DETAIL-Werts werden mit
  ";" getrennt, NICHT mit "," -- das Komma bleibt ausschliesslich der
  Trenner zwischen den k:v-Paaren selbst (Escaping-Regel aus diesem Abschnitt).

6. ENTSCHIEDEN
-----------------
  1. AVX/AVX2-Erkennung: PROAKTIV ueber CPU_FLAGS + CPU_CAPABILITY_TAGS
     (siehe Abschnitt 1b). Kein Warten auf einen ersten Crash mehr.
  2. hw_hash-Basis: (CPU_ARCH, PLATFORM, OS_BITNESS, CORE) -- siehe Abschnitt 1.
  3. DETAIL-Feld wird escaped ("|" und "," werden maskiert) -- siehe Abschnitt 4.
  4. Status-Schluessel pro Modul: PIP_NAME, falls vorhanden (Position "Pip
     Install Name" im Tuple); ist keiner angegeben (None/fehlt), wird der
     IMPORT-NAME als Schluessel genutzt (bei LIBRARY_FROM: das MODULE-Feld,
     also z.B. "torch.nn.functional" -> Schluessel "torch", weil pip_name
     dort explizit "torch" ist). So landen torch / torch.nn.functional /
     torchvision unter zwei Schluesseln ("torch" und "torchvision"), nicht
     unter drei -- das entspricht der tatsaechlichen Installationseinheit.
  5. GPU_RAM: INFORMATIV fuer spaetere Schritte, kein Vorfilter-Kriterium.
     Grund: GPU-Erkennung (CUDA vorhanden? welche Compute Capability?)
     ist ein eigenes, groesseres Thema und wuerde diese Ablauf-Skizze
     sprengen. GPU_RAM wird im HARDWARE_INFORMATION-Block miterfasst und
     mitgeloggt, fliesst aber (noch) nicht in Abschnitt 1b (proaktiver
     Vorfilter) ein. Kann spaeter nachgezogen werden, sobald GPU-bezogene
     patterns_filterung-Tags (z.B. "CUDA") definiert sind.

  LOG_FILE_NAME = "LOG_ai_loghic_agent_LOG.log"
  MAX_RETRIES   = 2
 
  Log-Pfad-Ermittlung ueber get_project_root():
    - sucht ab dem aktuellen Arbeitsverzeichnis bis zu 7 Ebenen nach oben
      nach einem "src"-Ordner (oder erkennt, ob man selbst bereits in "src" steht)
    - LOGS_DIR = PROJECT_ROOT / "logs"  (wird bei Bedarf angelegt)
    - TARGET_LOG_PATH = LOGS_DIR / LOG_FILE_NAME
 
  LIBRARY_IMPORT und LIBRARY_FROM: wie vom Nutzer vorgegeben, Tuple-Struktur
    LIBRARY_IMPORT: (Import Name, Alias, Pip Install Name, version_constraint, patterns_filterung)
    LIBRARY_FROM:   (Module, Import Target, Alias, Pip Install Name, version_constraint, patterns_filterung)
