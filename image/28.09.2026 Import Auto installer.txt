ABLAUF-LOGIK: AUTO-IMPORT & KOMPATIBILITAETS-AGENT
====================================================
Reine Planungsskizze (kein Code). Ziel: exakte Begriffe, Datenfelder und
Log-Zeilenformat festlegen, bevor irgendetwas implementiert wird.
 
 
1. DATENFELDER PRO HARDWARE-PROFIL (HARDWARE_INFORMATION)
------------------------------------------------------------
Erfasst einmal pro Programmstart, bevor irgendein fremdes Paket importiert wird.
Feldnamen wie vorgegeben (Grundgeruest):
 
  Feldname        Typ     Quelle                            Zweck
  --------------  ------  --------------------------------  -------------------------------
  CORE            int     os.cpu_count() / psutil            Kern-/Thread-Anzahl (informativ)
  RAM             float   psutil.virtual_memory().total      informativ, evtl. Grenzwert-Filter
  GPU_RAM         float   optional, falls GPU erkennbar       informativ (CUDA-Pakete)
  PLATFORM        str     platform.system()                  Windows / Linux / Darwin
  OS_BITNESS      str     platform.architecture()            32bit / 64bit
  CPU_ARCH        str     platform.machine()                 z.B. AMD64, x86_64, ARM64
 
Zusaetzlich, NICHT Teil der sechs Grundfelder, aber fuer den proaktiven
Vorfilter zwingend noetig:
 
  Feldname        Typ           Quelle                       Zweck
  --------------  ------------  ---------------------------  -------------------------------
  CPU_FLAGS       set[str]      CPUID via ctypes             Menge unterstuetzter Instruction-
                                                               Sets, z.B. {"AVX","AVX2","SSE4"}
  pc_id           str           Vergabe durch Log (PC1,PC2..) kompakter Schluessel im Log
  hw_hash         str           Hash ueber Felder oben        Wiedererkennung derselben Maschine
 
  hw_hash = Hash ueber (CPU_ARCH, PLATFORM, OS_BITNESS, CORE) -- OHNE RAM/GPU_RAM,
  da diese sich z.B. durch RAM-Nachruesten aendern koennen, ohne dass es eine
  "neue" Maschine ist.
  CPU_FLAGS ist eine Eigenschaft, kein Identitaetsmerkmal -> fliesst NICHT in den Hash ein.
 
 
1b. PROAKTIVE AVX/AVX2-ERKENNUNG UEBER patterns_filterung
--------------------------------------------------------------
Das Feld "patterns_filterung" (5. Tupel-Element in LIBRARY_IMPORT/LIBRARY_FROM)
hat zwei verschiedene Inhaltsarten, die getrennt behandelt werden:
 
  a) FAEHIGKEITS-TAGS  (feste Whitelist, siehe unten)
     Beispiel: ["AVX2"], ["AVX", "AVX2", "AVX512"]
     -> werden VOR jedem Importversuch gegen CPU_FLAGS geprueft.
     -> Tag nicht in CPU_FLAGS enthalten => PHASE=FILTER EVENT=SKIP_HW,
        Status=HW_INCOMPATIBLE, kein Import-/Install-Versuch.
 
  b) FEHLERTEXT-MUSTER  (alles, was NICHT auf der Whitelist steht)
     Beispiel: ["0x45a", "WinError 1114"]
     -> werden NUR verwendet, falls trotzdem ein Fehler auftritt
        (zusammen mit der globalen patterns[]-Liste), also reaktiv,
        PHASE=INSTALL EVENT=BANNED.
 
  CPU_CAPABILITY_TAGS (feste Whitelist, bestimmt a) vs. b)):
    { "AVX", "AVX2", "AVX512", "FMA", "BMI2", "SSE4" }
 
  Damit ist z.B. bei torch (["AVX2"]) der komplette Inhalt ein Faehigkeits-Tag
  -> rein proaktiver Check. Bei tensorflow (["AVX","AVX2","0x45a","WinError 1114"])
  sind "AVX"/"AVX2" proaktiv, "0x45a"/"WinError 1114" bleiben reaktiv.
 
 
2. PC-ID VERGABE
------------------
  Format:   PC<N>          Beispiele: PC1, PC2, PC3 ...
  Regeln:
    - kein Unterstrich, kein fuehrendes Nullpadding
    - N steigt rein zaehlend mit jedem neuen hw_hash (kein Wiederverwenden
      von Luecken, falls ein Eintrag jemals entfernt wuerde)
    - naechste freie Nummer = Anzahl bisheriger HW_NEW-Eintraege + 1
 
 
3. BEGRIFFE FUER DEN MODUL-STATUS (pro PC_ID + Modulname)
-----------------------------------------------------------
  Status-Begriff       Bedeutung
  --------------------  --------------------------------------------------------
  UNKNOWN               noch nie versucht auf dieser PC_ID
  HW_INCOMPATIBLE        Vorfilter: Hardware kann es nicht (kein Versuch)
  OK                     Import erfolgreich, Modul im globalen Scope
  RETRYING               Fehler war "harmlos", RETRY_COUNT < MAX_RETRIES
  BANNED                 Fehler passte auf ein patterns_filterung-Muster -> aus
  RETRY_EXHAUSTED        RETRY_COUNT erreicht MAX_RETRIES, kein Hardwarefehler
 
 
4. LOG-ZEILENFORMAT (einzige Datenquelle, keine Zweitdatei)
---------------------------------------------------------------
Ein Eintrag pro Zeile, Reihenfolge fix, Layout mit eckigen Klammern/Pipes
fuer die Lesbarkeit:
 
  [PC_ID] | [JJJJ,MM,TT,hh,mm,ss] | [PHASE] | EVENT=<event> | MODULE=<name|-> | DETAIL=<freitext> | VERSUCH=<n|->
 
  PHASE  = grobe Kategorie, in der der Ablauf gerade steckt
  EVENT  = genauer Ausgang innerhalb dieser Phase
  VERSUCH = Versuchszaehler fuer dieses Modul auf dieser PC_ID ("-" wenn
            der Eintrag keinen Versuchsbezug hat, z.B. HW_NEW, SESSION_START)
 
  PARSING-METHODE (Aenderung ggue. vorheriger Fassung -- Erkenntnis aus dem
  Vorgaenger-Code): Es wird NICHT mehr naiv an "|" und "," gesplittet.
  Stattdessen wird jedes Feld per Label-Regex herausgezogen, z.B.
    r"\[PC_ID:\s*(PC\d+)\]"            -- fuer PC_ID
    r"MODULE=([^\|]*)\|"                -- fuer MODULE
    r"DETAIL=(.*)\|VERSUCH="            -- fuer DETAIL (bis zum naechsten Label)
  Vorteil: DETAIL darf beliebige Kommas/Pipes aus echten Fehlertexten
  enthalten, OHNE dass vorher escaped werden muss. Einzige Einschraenkung:
  DETAIL darf nicht zufaellig die literale Zeichenfolge "|VERSUCH=" enthalten
  (praktisch ausgeschlossen bei normalen Fehlertexten). Kein Escaping mehr
  noetig -- ersetzt die fruehere Escaping-Regel.
 
  PHASE -> moegliche EVENTs:
 
  PHASE       EVENTs
  ----------  ------------------------------------------------------------------
  HARDWARE    HW_NEW, HW_KNOWN
  SESSION     SESSION_START
  FILTER      SKIP_HW
  IMPORT      IMPORT_OK, IMPORT_FAIL
  INSTALL     INSTALL_TRY, INSTALL_OK, INSTALL_FAIL, RETRY, RETRY_EXHAUSTED, BANNED
  REPAIR      INLINE_REPAIR_TRY, INLINE_REPAIR_OK, INLINE_REPAIR_FAIL
 
  Beispielzeilen:
 
  [PC1]|[2026,09,27,10,15,03]|[HARDWARE]|EVENT=HW_NEW|MODULE=-|DETAIL=hash:8f3a1c,arch:AMD64,os:Windows,flags:SSE4;AVX|VERSUCH=-
  [PC1]|[2026,09,27,10,15,04]|[SESSION]|EVENT=SESSION_START|MODULE=-|DETAIL=-|VERSUCH=-
  [PC1]|[2026,09,27,10,15,05]|[FILTER]|EVENT=SKIP_HW|MODULE=torch|DETAIL=pattern:AVX2,benoetigt:AVX2|VERSUCH=-
  [PC1]|[2026,09,27,10,15,07]|[INSTALL]|EVENT=INSTALL_TRY|MODULE=faiss|DETAIL=pip_name:faiss-cpu|VERSUCH=1
  [PC1]|[2026,09,27,10,15,09]|[INSTALL]|EVENT=BANNED|MODULE=tensorflow|DETAIL=matched_pattern:WinError 1114, DLL init failed (voller, unveraenderter Fehlertext erlaubt)|VERSUCH=2
  [PC2]|[2026,09,27,11,02,00]|[HARDWARE]|EVENT=HW_NEW|MODULE=-|DETAIL=hash:2b91f0,arch:ARM64,os:Linux,flags:SSE4;AVX;AVX2|VERSUCH=-
 
  Hinweis: mehrere CPU_FLAGS-Werte innerhalb EINES DETAIL-Werts werden weiterhin
  mit ";" getrennt (reine Lesbarkeits-Konvention, kein Parsing-Zwang mehr).
 
 
5. GESAMT-ABLAUF (Textskizze)
--------------------------------
 
  [0] SESSION_START
      Log-Datei oeffnen (anlegen falls nicht vorhanden)
              |
              v
  [1] HARDWARE_INFORMATION erfassen
      CPU_ARCH, CPU_FLAGS, CORE, RAM, GPU_RAM, PLATFORM, OS_BITNESS
      -> HW_HASH berechnen (Basis: CPU_ARCH, PLATFORM, OS_BITNESS, CORE)
              |
              v
      HW_HASH bereits im Log?
        JA  -> PHASE=HARDWARE EVENT=HW_KNOWN   -> PC_ID uebernehmen
        NEIN -> PHASE=HARDWARE EVENT=HW_NEW    -> naechste freie PC<N> vergeben
              |
              v
  [2] Log nach PC_ID filtern
      -> Modul-Status-Tabelle im Speicher aufbauen:
         { modulname: status, retry_count, matched_pattern }
              |
              v
      Fuer jedes Modul aus LIBRARY_IMPORT + LIBRARY_FROM:
              |
              v
  [3] Status-Check aus Speicher
      BANNED / RETRY_EXHAUSTED  -> SKIP (kein neuer Versuch)
      HW_INCOMPATIBLE           -> SKIP
      OK                        -> direkt importieren
      UNKNOWN / RETRYING        -> weiter zu [4]
              |
              v
  [4] Vorfilter: FAEHIGKEITS-TAGS aus patterns_filterung vs. CPU_FLAGS (siehe 1b)
      z.B. Tag "AVX2" im patterns_filterung des Moduls UND "AVX2" NICHT in CPU_FLAGS
      -> PHASE=FILTER EVENT=SKIP_HW, Status=HW_INCOMPATIBLE,
         weiter zum naechsten Modul (kein Import-/Install-Versuch)
              |
              v (Hardware passt)
  [5] Lokaler Import-Versuch (importlib)
              |
      +-------+-------+
      |               |
   ERFOLG           FEHLER
      |               |
      v               v
  PHASE=IMPORT    [6] Fehlertext gegen patterns[] matchen
  EVENT=IMPORT_OK          |

                   MATCH         NO MATCH
                    |               |
                    v               v
          PHASE=INSTALL      RETRY_COUNT < MAX_RETRIES?
          EVENT=BANNED         NEIN            JA

           Versuch)     PHASE=INSTALL     PHASE=INSTALL
                         EVENT=RETRY_      EVENT=INSTALL_TRY
                         EXHAUSTED         pip install <pip_name><version>
                         Status=           VERSUCH=<n+1>
                         RETRY_EXHAUSTED           |
                                          +---------+---------+
                                        FEHLER              ERFOLG
                                          |                    |
                                          v                    v
                                PHASE=INSTALL         Re-Import-Versuch
                                EVENT=INSTALL_FAIL             |
                                EVENT=RETRY (count+1)  +--------+--------+
                                Status=RETRYING       ERFOLG          CRASH
                                                        |                |
                                                        v                v
                                              PHASE=IMPORT      PHASE=REPAIR
                                              EVENT=IMPORT_OK   EVENT=INLINE_REPAIR_TRY

6. ENTSCHIEDEN
-----------------
  1. AVX/AVX2-Erkennung: PROAKTIV ueber CPU_FLAGS + CPU_CAPABILITY_TAGS
     (siehe Abschnitt 1b). Kein Warten auf einen ersten Crash mehr.
  2. hw_hash-Basis: (CPU_ARCH, PLATFORM, OS_BITNESS, CORE) -- siehe Abschnitt 1.
  3. DETAIL-Feld: KEIN Escaping mehr -- stattdessen Label-basierte Regex-
     Extraktion (siehe Abschnitt 4). Aenderung ggue. vorheriger Fassung,
     ausgeloest durch die Analyse des Vorgaenger-Codes.
  4. Status-Schluessel pro Modul: IMMER der Top-Level-Import-Name
     (mod_name.split(".")[0]), z.B. "torch.nn.functional" -> "torch".
     Vereinfacht ggue. vorheriger Fassung (kein PIP_NAME-Vorrang mehr noetig,
     da beide Regeln in der vorliegenden LIBRARY_IMPORT/LIBRARY_FROM-Liste
     ohnehin zum selben Ergebnis fuehren; Top-Level-Name ist die einfachere
     Regel und entspricht dem bewaehrten Vorgaenger-Ansatz).
  5. GPU_RAM: INFORMATIV fuer spaetere Schritte, kein Vorfilter-Kriterium.
     Grund: GPU-Erkennung (CUDA vorhanden? welche Compute Capability?)
     ist ein eigenes, groesseres Thema und wuerde diese Ablauf-Skizze
     sprengen. GPU_RAM wird im HARDWARE_INFORMATION-Block miterfasst und
     mitgeloggt, fliesst aber (noch) nicht in Abschnitt 1b (proaktiver
     Vorfilter) ein. Kann spaeter nachgezogen werden, sobald GPU-bezogene
     patterns_filterung-Tags (z.B. "CUDA") definiert sind.
  6. AUDIT-LOG-UMFANG (ANNAHME, bitte bestaetigen oder korrigieren):
     Hybrid-Ansatz -- EVENT=IMPORT_OK wird pro PC_ID+Modul nur EINMAL
     geschrieben (beim ersten erfolgreichen Import), nicht bei jedem
     einzelnen Programmlauf erneut. Grund: haelt das Log schlank (wie im
     Vorgaenger, der Erfolge gar nicht loggt), behaelt aber im Gegensatz
     zum Vorgaenger trotzdem einen Nachweis, WANN ein Modul zum ersten Mal
     funktioniert hat. Falls ein voller Audit-Trail (jede OK-Zeile bei
     jedem Lauf) gewuenscht ist, muss das explizit geaendert werden.
  7. VC++-REDISTRIBUTABLE BEI WinError 1114 (ANNAHME, bitte bestaetigen
     oder korrigieren): NUR ERKENNEN + IM LOG EMPFEHLEN, KEIN automatischer
     Download/Silent-Install einer .exe aus dem Netz. Grund: das ist ein
     Eingriff auf Systemebene ausserhalb von pip/Python und sollte nicht
     ohne Zustimmung automatisch laufen. Der Vorgaenger-Code macht das
     automatisch (Download + "/passive /norestart") -- das wird NICHT
     uebernommen, es sei denn, das wird ausdruecklich gewuenscht.
 
 
7. BESTAETIGTE KONSTANTEN & LISTEN FUER DIE IMPLEMENTIERUNG
------------------------------------------------------------------
  LOG_FILE_NAME = "LOG_ai_loghic_agent_LOG.log"
  MAX_RETRIES   = 2
 
  Log-Pfad-Ermittlung ueber get_project_root():
    - sucht ab dem aktuellen Arbeitsverzeichnis bis zu 7 Ebenen nach oben
      nach einem "src"-Ordner (oder erkennt, ob man selbst bereits in "src" steht)
    - LOGS_DIR = PROJECT_ROOT / "logs"  (wird bei Bedarf angelegt)
    - TARGET_LOG_PATH = LOGS_DIR / LOG_FILE_NAME
 
  LIBRARY_IMPORT und LIBRARY_FROM: wie vom Nutzer vorgegeben, Tuple-Struktur
    LIBRARY_IMPORT: (Import Name, Alias, Pip Install Name, version_constraint, patterns_filterung)
    LIBRARY_FROM:   (Module, Import Target, Alias, Pip Install Name, version_constraint, patterns_filterung)
  Inhalt (Kategorien): Standard-Bibliotheken, Data Science, Netz-Utilities,
    AI/LLM/Hubs, Vektor-Suche & NLP, Vision & Deep Learning, Geodaten,
    ML & Time Series, Audio & Interaktivitaet -- exakte Listen siehe
    separates Code-Dokument (nicht Teil dieser Ablauf-Skizze).
 
  PLATTFORM-SPEZIFISCHE PIP-NAMEN (uebernommen aus Vorgaenger-Code):
    - tensorflow  + PLATFORM=Darwin + CPU_ARCH=arm64  -> Pip-Paket "tensorflow-macos"
                    statt "tensorflow" (Apple Silicon)
    - torch / torchvision + PLATFORM=Windows -> Installation ueber separaten
                    CPU-Wheel-Index (https://download.pytorch.org/whl/cpu),
                    sonst laedt pip standardmaessig die grosse CUDA-Variante
 
 
8. UEBERNOMMENE MUSTER AUS DEM VORGAENGER-CODE
------------------------------------------------------------------
  1. Python-Standard "logging" als Log-Backend (statt eigenem File-Writer):
     Format "%(asctime)s [PC_ID: ...] [%(levelname)s] %(message)s",
     gleichzeitig StreamHandler (Konsole) + FileHandler (Datei).
  2. Label-basierte Regex-Extraktion statt striktem Spalten-Split (siehe
     Abschnitt 4) -- macht Escaping ueberfluessig.
  3. Plattform-Sonderfaelle bei Pip-Namen (siehe Abschnitt 7).
  4. Status-Schluessel = Top-Level-Import-Name (siehe Abschnitt 6, Punkt 4).
  5. Zwei-stufige Reparatur bei Installationsfehlern: normaler Install ->
     bei erneutem Fehlschlag EIN Force-Reinstall-Versuch (--force-reinstall)
     -> erst danach BANNED. Deckt sich mit unserem REPAIR-Ablauf (Abschnitt 5).
 
 
9. BEKANNTE FEHLER AUS DEM VORGAENGER-CODE (NICHT UEBERNEHMEN)
------------------------------------------------------------------
  1. has_avx2_support() prueft NUR unter Linux echt (liest /proc/cpuinfo);
     unter Windows/macOS gibt die Funktion immer "True" zurueck --
     genau auf den Plattformen, auf denen die meisten Fehlermuster
     (WinError 1114, not a valid Win32 application) ueberhaupt auftreten.
     Damit war der proaktive Vorfilter unter Windows faktisch wirkungslos.
     -> In dieser Skizze wird CPU_FLAGS plattformuebergreifend per
     CPUID/ctypes ermittelt (Abschnitt 1), nicht per /proc/cpuinfo-Textsuche.
  2. check_hardware_compatibility() im Vorgaenger prueft nur die Tags
     "AVX2" und "32BIT" explizit -- das reine Tag "AVX" (ohne die "2") wird
     nie behandelt und faellt bei z.B. tensorflow (["AVX","AVX2",...])
     stillschweigend durch. -> Abschnitt 1b verwendet stattdessen eine
     generische Whitelist (CPU_CAPABILITY_TAGS) mit Mengenvergleich gegen
     CPU_FLAGS, damit KEIN Tag mehr uebersehen werden kann.
  3. HW_KEY im Vorgaenger basiert auf MAC-Adresse und RAM-Groesse. Beides
     kann sich aendern, ohne dass es sich um eine neue Maschine handelt
     (MAC bei neuem Netzwerkadapter/VPN, RAM bei Aufruestung) -- das wuerde
     faelschlich eine neue PC_ID erzeugen. -> HW_HASH-Basis in dieser
     Skizze bewusst OHNE MAC/RAM (siehe Abschnitt 1, Entscheidung 2).
  4. Erfassung von CORE, OS_BITNESS, GPU_RAM, CPU_FLAGS fehlt komplett im
     Vorgaenger -- wird in dieser Skizze neu definiert (Abschnitt 1).
  5. Automatischer Download + Silent-Install (.exe aus dem Netz) beim
     VC++-Redistributable-Fix ohne Rueckfrage -- wird NICHT uebernommen
     (siehe Abschnitt 6, Entscheidung 7: nur Erkennung + Empfehlung im Log).
